## Ошибки и риски по приоритету

### 1. P1 — ошибка API может стать «успешным пустым сбором»

Код: `insta_html_export.py:1168`, `:2122`, `:2582`.

REST timeline и comments проверяют HTTP-код, но не требуют успешного тела ответа
и нужной структуры. Ответ HTTP 200 с `{"status":"fail","message":"login_required"}`
интерпретируется как пустой список. Для комментариев воспроизведение дошло до
`exit_code=0`, `completed_posts=["A"]`, нуля записей. Повторный запуск пропустит такой
пост как уже обработанный. REST вернул `([], None, False)`, то есть видимость конца ленты.

Исправление: общая проверка семантики ответа, обязательных полей и типов; отдельные
состояния «пусто», «доступ запрещён», «ответ неизвестной формы», «неполно». Тестировать
HTTP 200 с ошибкой, login/checkpoint и отсутствующими полями.

### 2. P1 — «последние N» зависят от порядка ленты, а не времени публикации

Код: `insta_html_export.py:1775`, `:1822`.

Без фильтра дат функция сразу возвращает исходные ссылки, затем берёт первые N.
При входном порядке «старый закреплённый A, новый B» и `--limit 1` выбирается A,
хотя timestamps обоих постов уже известны. При фильтре дат сортировка использует
только календарный день и не различает время внутри дня.

Исправление: нормализовать порядок по полному timestamp, определить поведение для
закреплённых и совместных публикаций, использовать стабильный дополнительный ключ.
Не обещать точный выбор последних/первых N при неизвестных датах.

### 3. P1 — обычный повторный запуск не гарантирует обнаружение новых постов

Код: `insta_html_export.py:1377`, `:1857`, `:2543`.

Для завершённого кеша и неизвестного общего количества лента не проверяется вообще.
Воспроизведение: одна сохранённая ссылка, `completed=True`, total=0 → ноль запросов
страниц и возврат старой ссылки. При увеличении известного total с 1 до 2 первый
повтор тоже не получает новую страницу: возвращает один пост и помечает кеш неполным.
Следующая попытка может начать обход заново, но первая уже не выполняет ожидаемое обновление.

Это частично соответствует текущей ориентации на возобновление, но команды «продолжить»
и «обновить данные» должны иметь ясную семантику. `--refresh` существует, однако слишком
грубо связывает обновление ленты с повторной обработкой содержимого.

Исправление: отдельный режим обновления/инкрементального сканирования; проверять свежую
голову ленты, объединять по shortcode, хранить время последней проверки, не перескачивать
неизменившиеся медиа. Политику обновления закреплений/удалений описать явно.

### 4. P2 — обрыв комментариев теряет прогресс внутри текущего поста

Код: `insta_html_export.py:2160`, `:2582`.

Все страницы комментариев накапливаются в памяти и сохраняются только после успеха
всего поста. Воспроизведение: первая страница с комментарием получена, вторая падает
с ConnectionError → `.comments.json` не создан, первая страница не сохранена.
Другие уже завершённые посты остаются в кеше, но текущий нужно проходить сначала.

Исправление: хранить страницы и курсор в SQLite по аналогии с лайками; сохранять
`collecting/partial/failed/complete`, дедуплицировать по comment ID. Сбор ответов на
комментарии — отдельная будущая функция: сейчас отчёт честно предупреждает, что их может не быть.

### 5. P2 — специальный текст подписи ломает отображение HTML-архива

Код: `insta_html_export.py:1693`, `igdump_assets/index.html:541`.

JSON в script-блоке экранирует `</`, но оставляет `<`. Подпись `<!--<script>`
переводит HTML-парсер в особое состояние. Проверка в Chrome: обычная подпись —
1 карточка и 2 script-элемента; проблемная — 0 карточек и 1 script-элемент.
Выполнение внедрённого JavaScript не подтверждено; подтверждён отказ отображения архива.

Исправление: единый безопасный JSON serializer для HTML, как минимум `<` → `\u003c`;
проверить также `>`, `&` и комбинации script/comment delimiters в браузерных тестах.
В пассивных отчётах экранирование `<` уже применяется.

### 6. P2 — устаревший счётчик лайков создаёт ложную неполноту

Код: `insta_html_export.py:2684`, `:2707`.

Применяется максимум сохранённого и нового количества. Если раньше лайков было 5,
а сейчас API сообщил 3 и вернул всех троих, программа сохраняет expected=5 и partial.
Это воспроизведено; затем выполняются бесполезные повторные проверки.
Кроме того, накопленные пары пользователь/пост без refresh представляют объединение
наблюдений разных моментов, а не обязательно текущее состояние списка.

Исправление: хранить источник и время счётчика, отдавать приоритет свежему согласованному
снимку; различать текущий список и исторически наблюдавшихся пользователей. Это не
устраняет реальные ограничения Instagram на доступные списки.

### 7. P2 — самостоятельные likes/comments не используют весь новый Chrome fallback

Код: `insta_html_export.py:2422`, особенно `:2482` и `:2518`.

По коду браузер открывается для извлечения cookies и закрывается до разрешения профиля.
Далее используется `fetch_profile_info`, а не `resolve_profile_for_posts`, нет сохранённой
живой страницы с наблюдаемым запросом пагинации. Поэтому fixes, помогающие posts/full,
не обеспечивают такое же поведение самостоятельным командам. Живой отказ этих команд
в этом аудите не воспроизводился; расхождение путей подтверждено чтением кода.

Исправление: общий объект сессии/транспорта с жизненным циклом на весь сбор и единый
сервис получения профиля/ленты. Сохранить возможность работы через sessionid.

### 8. P2 — служебный CSRF-заголовок уходит вместе со скачиванием медиа

Код: `insta_html_export.py:258`, `:611`.

Авторизованная Session используется и для Instagram, и для внешнего URL изображения.
В проверке подготовленного запроса к `https://cdn.example/avatar.jpg` присутствует
`X-CSRFToken`. Instagram cookie `sessionid` туда не передаётся: доменная привязка работает.
Подтверждено распространение лишнего заголовка, а не кража сессии или захват аккаунта.

Исправление: отдельная сессия скачивания медиа без Instagram cookies и auth-заголовков;
разрешать HTTPS, проверять перенаправления и тип содержимого. При копировании cookies
из Chrome сохранить и их атрибут secure/expiry, а не только domain/path.

### 9. P2 — окружение и допустимые зависимости требуют обновления

`pyproject.toml:8` и `requirements.txt` допускают Requests 2.31; именно 2.31.0 установлен
в текущем окружении. Официальные advisories включают:

- [утечку .netrc при специально сформированном URL, исправлено в 2.32.4](https://github.com/psf/requests/security/advisories/GHSA-9hjg-9r4m-mvj7);
- [небезопасное повторное использование временного файла в extract_zipped_paths, исправлено в 2.33.0](https://github.com/psf/requests/security/advisories/GHSA-gc5v-m9x4-r6x2).

Наличие уязвимой версии не доказывает эксплуатацию: эти advisories требуют своих
условий. Сценарий verify=False из другого advisory в коде igdump не найден.

`pip check` также обнаружил конфликты requests/dnspython с установленными mailspoof
и osint-notebook. Это конфликты общего окружения, а не доказательство поломки igdump.

Исправление: выделенное venv, повышение минимально допустимых версий после проверки
совместимости, воспроизводимый набор проверенных зависимостей и автоматическая проверка
advisories в CI. Не обновлять общий Python вслепую: это может затронуть другие инструменты.
Sessionid сейчас хранится открытым текстом; отдельно нужны ограничение доступа к файлу
и скрытый ввод вместо обычного input. Содержимое пользовательского config не читалось.

## Где теряется время

Свежий сохранённый журнал охватывает 1 589,6 с, то есть примерно 26 мин 30 с.
В архиве 112 постов и 705 медиафайлов — размер задачи заметно больше числа постов.

| Категория | Зарегистрировано ответов | Сумма записанных elapsed_ms |
| --- | ---: | ---: |
| Медиа/CDN | 705 | 235,2 с |
| Комментарии | 112 | 84,9 с |
| Лайки | 143 | 152,9 с |
| GraphQL через Chrome | 8 | Не измеряется этим журналом |
| Остальное Instagram | 1 | 0,5 с |

Для потокового скачивания elapsed_ms измеряет получение ответа до чтения всего тела.
Эта таблица не является полным профилем сетевого времени. Запросы, инициированные самой
страницей Chrome, тоже не все входят в счётчик. Остаток времени нельзя целиком объявлять ожиданием.

В 143 запросах лайков не было курсора max_id: 31 запрос сверх числа постов связан
с повторным чтением списков. При стандартных паузах в 2 с 255 запросов комментариев/лайков
дают номинально 510 с ожидания плюс jitter. Только 31 дополнительная проверка добавляет
номинально 62 с пауз и сетевое время. Сокращать паузы вслепую не следует.

Первоочередные ускорения:

1. **Использовать полные payload постов из уже полученной ленты.** Сейчас
   `remember_details` оставляет компактные данные без медиа, а `run:1962` открывает
   отдельную страницу каждого отсутствующего в кеше поста. Если timeline payload
   достаточен, это лишняя навигация. Оставить fallback для неполных payload и протухших URL.
2. **Останавливать обход для последних N, когда выбор уже доказан.** Сейчас
   `--limit 1` в проверке всё равно запросил все 3 страницы. Учитывать закреплённые
   посты и даты; для `--oldest` полный обход часто действительно необходим.
3. **Разделить сохранение прогресса и HTML-рендер.** На каждом посте переписываются
   растущие JSON и весь HTML; metadata сохраняется и перед checkpoint, и внутри него.
   По объёму повторной сериализации это даёт квадратичный рост. Хранить прогресс
   транзакционно, обновлять HTML каждые несколько постов/секунд и при завершении.
4. **Ограниченная параллельная загрузка медиа**, например 2–4 рабочих потока с отдельными
   сессиями. Сначала измерить тело скачивания и влияние на ошибки; не переносить такую
   параллельность автоматически на Instagram GraphQL/likes/comments.
5. **Управляемая перепроверка неполных лайков:** интервал, причина, fingerprint списка,
   возможность отключить немедленную проверку. Не менять принятую полноту или дефолты молча.

Точный коэффициент ускорения без реализации и сравнения на одинаковом наборе постов
обещать нельзя. Главные кандидаты — навигация по каждому посту и загрузка 705 файлов.

## Хранение, интерфейс и сопровождение

- Разделить архив данных профиля и выбранное представление. Сейчас `.export-state.json`
  привязан к limit/mode/date и содержит только текущую выборку. Смена выборки в том же
  output-dir перезаписывает этот индекс; старые медиа могут остаться без записей архива.
- Нужен lock на каталог экспорта. JSON пишет через общий `<name>.tmp`; два процесса
  в одну папку могут столкнуться. Действующий SQLite сам по себе не защищает JSON/HTML.
- Повреждённый JSON сейчас тихо трактуется как отсутствие кеша. Лучше сообщение,
  резервная копия и явное восстановление, чтобы не запускать неожиданный полный пересбор.
- HTML/CSV записываются напрямую. Применить атомарную замену и к финальным отчётам.
- Разделить «успешно сформирован офлайн-отчёт» и «все данные собраны»: offline-функции
  возвращают 0 даже для неполного архива; full может подписать такую фазу complete.
- Добавить в отчёты время снимка, полноту медиа/комментариев/лайков, источник полей,
  явный часовой пояс фильтров. Изменение зоны графика сейчас не меняет CLI-фильтры —
  это нормально, но календарные даты в кеше нельзя незаметно переносить между зонами.
- HTTP-счётчик должен объяснять, что учитывает; текущий не охватывает весь трафик Chrome.
  Добавить тайминги фаз, байты загрузки, число повторов, cache hits, версии программы/схемы.
- Обрабатывать неизвестную форму JSON, PlaywrightError на уровне запуска и OSError диска
  общим завершением с сохранением статуса. Сейчас часть таких исключений выходит наружу
  traceback, минуя ожидаемую финальную индикацию.
- У комментариев сохранять user ID и агрегировать по нему: username может смениться.
- Карты и контакты при большом числе строк потребуют пагинации/виртуализации. Сейчас
  HTML содержит все строки; расположение подписей карты перебирает уже размещённые подписи.
  Для сотен/тысяч координат нужны кластеризация и фильтры дат.
- Основной модуль — около 2 900 строк с CLI, HTTP, кешем и HTML. Разделить transport,
  timeline, media, comments/likes, orchestration и reports. Динамические `_igdump_*`
  атрибуты Session заменить явным контекстом запуска. Делать постепенно под тестами.
- В CI уже есть Ubuntu/Windows, Python 3.11/3.13 и проверка установленного CLI вне проекта.
  Добавить macOS, офлайн-браузерные тесты, сценарии из этого аудита, проверку wheel/assets,
  обновление версии релиза и журнал изменений. Нынешняя версия всё ещё 0.5.1.

## Что уже сделано хорошо

- Уникальные пары пользователь/пост в SQLite, сохранение страниц лайков и восстановление
  после неудачного refresh; атомарная замена JSON при одном процессе.
- Пассивные отчёты используют полученные данные, не обходят найденные контакты/ссылки
  и не запрашивают геокодирование. Кнопка подробной карты явно включает внешний источник.
- Защита CSV вынесена в одно место; обычный текст HTML экранируется. Найденный HTML-дефект
  касается отдельного способа размещения JSON, а не отсутствия экранирования вообще.
- Общая выборка и сессия в full, остановка зависимых фаз, причины неполных списков,
  отдельные курсоры GraphQL/REST, сохранение уже полученных ссылок.
- Реальные отчёты analytics/contacts/locations прошли локальную браузерную проверку;
  нет ошибок JS и горизонтального переполнения всей страницы на 390 px.
- Малый пакет: собранный wheel около 150 КиБ; карты не делают программу тяжёлой.

## Рекомендуемый порядок работ

1. Исправить ложный успех API, порядок публикаций, политику свежести кеша и JSON в HTML.
2. Сохранять страницы комментариев; исправить выбор свежего счётчика лайков;
   унифицировать авторизацию и отделить скачивание медиа от авторизованного транспорта.
3. Внедрить тайминги и повторное использование timeline payload, затем измерить
   ограниченную параллельную загрузку и более редкий HTML-рендер.
4. Изолировать окружение, обновить зависимости, расширить CI и постепенно разделить модули.

Новые функции стоит добавлять после первых двух этапов: иначе они будут опираться
на данные, которые в отдельных сценариях уже неполны или устарели.
